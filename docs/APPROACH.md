# Approach

## 1. What the task actually asks

Для каждого примера есть ровно два входа:

* `prompt` — полный контекст агента: системная инструкция, `<policy>`, `[AVAILABLE TOOLS]`,
  реплики пользователя, прошлые ходы агента, вызовы инструментов и их результаты;
* `response` — один проверяемый ход агента: текст клиенту и/или один-несколько `TOOL_CALL`.

Нужен бинарный флаг «есть ли в этом ходе контекстная галлюцинация». Условие задаёт
семантику:

1. **contradiction** — конкретное утверждение/действие противоречит контексту;
2. **unsupported** — конкретное утверждение не выводится из контекста, хотя и не
   противоречит ему;
3. всё, что «очевидно никогда не изменит итог» (пересказ, округление, форматирование,
   стиль, внутренние формулировки при верном результате) — **не** галлюцинация.

Ключевой критерий — «изменит ли это итог или данные, которые увидит пользователь?».

Отсюда следуют три вывода, определившие архитектуру:

* проверять нужно **конкретику**: числа, даты, id, имена, статусы, условия политики,
  имена и аргументы инструментов;
* нужен семантический разбор, потому что «не выводится из контекста» — это не строковое
  совпадение;
* нельзя штрафовать за стиль и пересказ, иначе precision рухнет.

Домены (`airline`, `retail`, `telecom`, `banking_knowledge`), формат политик и инструментов
совпадают с открытым бенчмарком **tau2-bench** (MIT). Это используется для генерации
синтетического devset и для проверки парсера (см. §7), но не для обучения: веса модели
не подгоняются под синтетику.

## 2. Pipeline

```
prompt/response
   │
   ├─ transcript.py  ── события: system | user | assistant | tool_call | tool_response
   │                     (терпит многострочный JSON, ...-усечения, отсутствие стрелок)
   ├─ toolspec.py    ── каталог инструментов + схемы аргументов
   ├─ signals.py     ── hard/soft сигналы
   │
   ├─ если hard-сигнал (rule_mode=strict) ──► label=1, GPU не нужен
   │
   ├─ evidence.py    ── бюджетная упаковка контекста (≤ ~10k токенов)
   ├─ prompts.py     ── рубрика + контекст + response + подсказки
   ├─ backends.py    ── vLLM (по умолчанию) / transformers / без модели
   ├─ judge.py       ── JSON-вердикт, self-consistency, fallback
   └─ fusion.py      ── финальная метка и score
```

### 2.1. Парсер

Маркеры `⟦SYSTEM⟧`, `⟦USER⟧`, `⟦ASSISTANT · ход N⟧` могут стоять как отдельной строкой,
так и с ведущими пробелами; поддерживаются латинские `turn/step` и маркеры без номера хода.
Строки инструментов:

```
→ TOOL_CALL name: {json}
← TOOL_RESPONSE name: {json или текст}
```

* JSON может быть pretty-printed на нескольких строках — балансировка скобок с учётом строк;
* стрелка может отсутствовать — есть запасной regex;
* текстовый tool-ответ может занимать несколько строк с отступом — собирается по отступу;
* `{...}` с многоточием не считается ошибкой: аргументы не парсятся, но видимые
  идентификаторы всё равно проверяются.

`response` парсится тем же кодом, поэтому текст и вызовы инструментов разделяются корректно.

### 2.2. Каталог инструментов

`[AVAILABLE TOOLS]` разбирается в двух форматах:

* JSON-схемы (OpenAI `{"type":"function","function":{...}}`, список схем, словарь `name → schema`);
* текстовый формат tau2 `Tool: name / Description: / Parameters: - arg: type (required) - ...`.

Для каждого инструмента извлекаются `required`, типы, `enum`, `additionalProperties`.
Если каталог не найден, проверки доступности/схемы отключаются (чтобы не давать ложных
срабатываний на нестандартном рендере).

## 3. Детерминированные сигналы

| Сигнал | Уровень | Что проверяет |
|---|---|---|
| `tool_not_available` | **hard** | имя инструмента отсутствует в каталоге (с допуском на суффикс `_1234` у discoverable-инструментов) |
| `invalid_tool_arguments` | **hard** | нет required-поля, неверный тип, значение вне `enum`, лишнее поле при `additionalProperties=false` |
| `ungrounded_argument` | **hard** | строковый аргумент вида `*_id` / `*_number` / `*_code` не встречается в контексте |
| `ungrounded_email/phone/order_id/doc_id/code` | **hard** | идентификатор из текста ответа не встречается в контексте |
| `ungrounded_number` | soft | денежная сумма/дата/время из ответа не найдены дословно (может быть округлением или суммой) |
| `missing_confirmation` | soft | изменяющий состояние вызов без явного подтверждения пользователя, при политике, требующей подтверждения |
| `possible_false_refusal` | soft | отказ/«нет доступа» при наличии инструментов и политики, которые могут разрешать запрос |
| `claimed_action_without_tool_call` | soft | «я отменил/оформил/отправил», но в ходе нет вызова инструмента |
| `action_targets_unrequested_entity` | soft | действие меняет сущность, которую пользователь не упоминал |
| `claimed_success_after_tool_error` | soft | «успешно отменил», хотя последний tool-ответ содержит ошибку |
| `duplicate_tool_call` | soft | повтор предыдущего вызова с теми же аргументами |
| `unparseable_arguments` | soft | JSON аргументов не парсится и не содержит многоточия |

Почему hard-список именно такой: каждая категория **прямо перечислена в условии** как
галлюцинация («вызов недоступного инструмента», «неверные аргументы», «ссылка на сущность,
которой нет в данных»). Всё, что требует интерпретации («не выводится», «нарушает правило»),
остаётся судье, чтобы не терять precision на косметике.

Идентификаторы в первую очередь ищутся в аргументах инструментов: действие над
несуществующей бронью — это ошибка действия, а не стилистика.

## 4. Упаковка контекста

Бюджет по умолчанию — 30k символов (≈10k токенов при оценке 3 символа/токен):

* **политика** — до 32% бюджета; если не влезает, сохраняется заголовок и те разделы,
  которые лексически пересекаются с проверяемым ходом (политики tau2 разбиты на `##`-секции);
* **каталог инструментов** — до 10%, имена + короткие описания;
* **диалог** — все реплики пользователя (до 1.8k символов каждая), ходы агента (до 700),
  вызовы инструментов (аргументы до 700);
* **tool-ответы** — ранжируются по:
  * лексическому пересечению с ответом (idf-подобная нормализация),
  * вхождению идентификаторов из ответа (сильный бонус),
  * свежести (последние 4 ответа — бонус),
  затем жадно набираются в бюджет; последний ответ включается всегда.

JSON-ответы сжимаются: длинные массивы сохраняют первые элементы + элементы, совпавшие
с запросом; длинные нерелевантные подобъекты отбрасываются; всё остальное усекается
посередине. Порядок событий при рендере сохраняется хронологическим, чтобы судья видел
причинно-следственную связь, а пропущенные ответы помечаются `[omitted to fit context]`.

На синтетическом наборе упаковка сохраняет **100% идентификаторов**, которые упоминает
ответ и которые есть в контексте (244/244), при среднем размере 20k символов.

## 5. Судья

Модель по умолчанию — `Qwen2.5-14B-Instruct-AWQ` через vLLM (вписывается в A100 40 ГБ,
≈9 ГБ весов). Альтернативы: 7B (быстрее), 32B (качественнее, но риск не уложиться в
30 минут), любой локальный путь через `--model-path`.

Промпт (см. `src/guardian/prompts.py`):

* определения всех пяти категорий с примерами;
* явный список того, что галлюцинацией **не** является (пересказ, агрегация, округление,
  стиль, вопросы на уточнение, опускание деталей);
* «decision test» из условия;
* процедура: разбить ответ на атомарные утверждения → найти цитату-доказательство →
  сравнить числа/id посимвольно → применить тест;
* калибровочные замечания: политика важнее слов агента; данные инструментов
  авторитетны; значения, названные пользователем ранее, заземлены; «NONE» = unsupported;
* два коротких примера (0 и 1) для формата и калибровки;
* строгий JSON-выход: `claims[]`, `label`, `hallucination_type`, `confidence`, `reason`.

В user-сообщение дополнительно попадают soft-сигналы как **подсказки** с пометкой
`weak`/`STRONG`; в промпте сказано, что они неполные и могут ошибаться.

Если ответ модели не парсится, делается один retry с требованием вернуть только JSON;
если и это не удалось — вердикт считается `failed` и используется rule-based fallback.

`self_consistency > 1` включает несколько сэмплов на пример (temperature 0.4) и мажоритарное
голосование; по умолчанию 1, так как бюджет времени ограничен.

## 6. Слияние и бюджет времени

```
if hard-сигнал and rule_mode == strict:  label = 1
elif judge доступен:                     p1 = confidence (или доля голосов)
                                         label = 1 if p1 >= threshold
else:                                    rule-based fallback
```

* `threshold` калибруется на публичном сплите (`scripts/calibrate.py`);
* `fusion.rule_mode = "hint"` превращает hard-сигналы в обычные подсказки (если на публичных
  данных окажется, что они дают ложные срабатывания);
* `signals.identifier_severity = "soft"` — то же для id-проверок;
* `fusion.soft_signal_override` позволяет включать `1` при накоплении soft-сигналов.

Бюджет времени: по умолчанию 1500 с из 1800 с лимита. После каждой батчи судья сравнивает
фактическую скорость с оставшимся временем; при риске превышения контекст для следующих
примеров ужимается (до 40% исходного бюджета). Если дедлайн всё равно достигнут, оставшиеся
примеры оцениваются правилами. Поэтому скрипт **всегда** завершает работу и пишет файл.

## 7. Валидация

`scripts/make_dev_from_tau2.py` собирает devset из tau2-bench:

* берутся только успешные симуляции (`reward == 1.0`) — их ходы считаются заземлёнными
  (метка 0);
* контекст рендерится в точном формате соревнования (системный блок с политикой и
  каталогом инструментов, история, `→/←`);
* контролируемые искажения дают однозначные положительные примеры:
  подмена денежной суммы, подмена id на несуществующий, добавление выдуманного факта,
  вызов несуществующего инструмента.

Результат на 180 примерах (airline/retail/telecom, 90/90):

| Режим | precision | recall | F1 |
|---|---|---|---|
| только hard-правила (`rule_mode=strict`) | 1.00 | 0.50 | 0.67 |
| rule-based fallback (hard + soft, без LLM) | 0.84 | 0.60 | 0.70 |

Разбивка recall по типу искажения:

| Искажение | Recall правил |
|---|---|
| вызов несуществующего инструмента | 1.00 |
| подмена id | ~1.00 (входит в contradiction) |
| подмена суммы | ~0.38 (soft-подсказка) |
| выдуманный факт | 0.00 (семантика — задача судьи) |

Это ожидаемо: правила закрывают «структурные» галлюцинации, а unsupported/contradiction
в тексте — работа LLM-судьи. Именно поэтому судья является основной ступенью, а правила —
гарантией на явных случаях и страховкой при нехватке времени/GPU.

Важно: синтетические метрики **не** являются оценкой на реальном сплите. Публичный сплит
нужно прогнать через `predict.py --with-details` и `calibrate.py`, чтобы получить честные
F1/precision/recall и подобрать порог.

## 8. Почему не обучение классификатора

Идея «извлечь эмбеддинги/open-source LLM и обучить LightGBM» требует доступа к публичному
датасету и GPU на этапе разработки. В офлайн-условии это невозможно проверить, а
непроверенная модель рискует оказаться хуже zero-shot судьи. Поэтому пайплайн построен
так, чтобы:

* работать zero-shot;
* калиброваться на публичных данных одной командой (порог + диагностика сигналов);
* при желании легко расширяться: `fusion.py` — единственное место, где принимается
  финальное решение, и туда можно добавить обученный классификатор поверх
  `(score, signal counts, длина ответа, домен)`.

## 9. Риски и что проверить на публичном сплите

1. **Доля положительных.** Если положительных мало (<20%), стоит поднять порог, чтобы
   не терять precision.
2. **Точность hard-сигналов.** Если `ungrounded_code` даёт ложные срабатывания на
   легитимных новых значениях — перевести в `soft`.
3. **Строгость судьи.** Если судья помечает косметику — усилить раздел «NOT a
   hallucination» и/или добавить self-consistency.
4. **Тайминг.** Замерить время на публичном сплите (548 примеров ≈ приватный), при
   необходимости уменьшить `max_prompt_tokens` или взять 7B.
5. **Формат `response`.** Если в реальных данных встречаются несколько `⟦ASSISTANT⟧`
   в одном ответе или нестандартные маркеры — парсер уже терпим, но стоит прогнать
   `--debug-jsonl` и посмотреть, не теряются ли события.
